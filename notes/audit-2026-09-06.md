# Project audit: image size and rebuild cost

Audited 2026-09-06, starting at `db5278b` with a clean working tree.

The main performance problem is the ownership-remapping copy performed for
`--userns=keep-id:uid=1000,gid=1000`. Reducing the image makes that copy
cheaper; ordinary Dockerfile cache optimization does not eliminate it. The
recommended first architectural change is to update the agent CLIs separately
from a stable runtime image. Moving the offline models outside the image is
the next largest reduction that preserves the current capabilities.

This audit preserves the current implementation. The changes below are
recommendations, not deployed fixes. In particular, no image-size improvement
or elimination of the host copy has been measured in this audit.

## Scope and evidence

Reviewed the Dockerfile, all host scripts, container entrypoint and configuration,
all installed and host-only helpers, CI, ignore/lint configuration, README, and
previous audit and ID-mapping notes. Agent credentials and conversation data were
not needed for the audit.

The available environment is itself a running ai-box-like container: Ubuntu
24.04, inner Podman 4.9.3/Buildah 1.33.7, rootless, with fuse-overlayfs. Its
`/etc/ai-box/versions` matches the Dockerfile's pinned tool versions and records
`ubuntu_refresh=2026-W36`. Its readable shared image store contains Alpine and
BusyBox; the host's `ai-box` image and native-overlay storage are not exposed.

Consequently:

- File sizes below are measured in the running filesystem using `du -sx -B1`.
  They are allocated bytes, expressed in MiB, and can include runtime changes.
  They are **not** compressed registry sizes or a sum of OCI layer tar sizes.
- The ~125-second/~8.5-GB host copy is previously measured evidence from
  [the September 4 investigation](idmap-2026-09-04.md), consistent with the
  current build/run scripts and upstream storage source. It was not timed again.
- A full rebuild, host cold/warm startup benchmark, host disk-write benchmark,
  and host termination/isolation acceptance test were not performed.
- This is a source, configuration, dependency-consistency, and focused runtime
  audit. It is not a complete CVE/SBOM or adversarial container-escape assessment.

## Why the whole image is copied

The normal rootless store maps container UID 0 to the host user. `bin/run`
instead maps UID 1000 to that user, so the image's stored ownership differs from
the requested mapping. On the recorded native-overlay host, there is no usable
mount-time shifting path. Storage creates a mapped alternative to the image's
top layer and changes ownership through the merged filesystem; this can copy
up files inherited from every lower layer. Upstream implementations are
[`imageTopLayerForMapping`](https://github.com/containers/storage/blob/main/store.go)
and the overlay driver's
[`UpdateLayerIDMap`/`SupportsShifting`](https://github.com/containers/storage/blob/main/drivers/overlay/overlay.go).

The cache of mapped alternatives is associated with the image. A filesystem
change producing a new image does not incrementally reuse the previous image's
mapped filesystem. Fully cached builds can reuse the existing image and mapped
alternative. Retagging the same image is not the same as rebuilding its files.
This is why a tiny helper or CLI update has a disproportionately large cost.

`bin/build` already moves this cost to build time by running a throwaway
container with the same mapping. That improves the next interactive launch but
does not remove the work. Its free-space delta measures overall filesystem space
change, not physical SSD writes attributable exclusively to Podman.

Do not repeat the two expensive experiments already recorded in the earlier
investigation: building with the runtime UID map, or changing an existing host
store to fuse-overlayfs without validating nested builds and shared storage.
The inspected upstream implementation still has the relevant limitations;
claims that they can *never* change in future versions are too strong.

### Recommended design: stable runtime, separately updated CLIs

Keep `bin/build` as the one user-facing update command, but have it perform two
independent operations:

1. Build/update the runtime on its existing weekly cadence or a runtime source
   change. Warm this image only as needed.
2. Resolve and install both CLIs into a separate small build/export target.
   Publish the completed files under `data/tools/<version-pair>/`; launch with
   that resolved directory mounted read-only at a dedicated path such as
   `/opt/ai-box-tools`, with its `bin` on PATH.

Use a temporary export directory, validate both `--version` commands, then
atomically update a local pointer. `bin/run` should resolve that pointer once
before mounting it. An unsuccessful update must leave the previous installation
usable. Retain versions used by running boxes; do not overwrite their files.
Avoid installing packages directly on the host or changing host npm settings.

This keeps the existing single-command workflow, fresh CLIs, fast offline
startup, and clone-local state. It requires the runtime and tool bundle together;
the image alone would no longer carry the CLIs. Ordinary container writes can
remain ephemeral. Weekly runtime updates and changes to helpers still baked into
the runtime would still incur remapping. Independent CLI stages *copied back
into the final image* would improve build caching but would not solve that.

The two current CLI package trees total about 525 MiB. Exporting them removes
those bytes from the runtime image, but still stores the tools on the host.
The important gain is avoiding a multi-gigabyte remap for a CLI-only update.
This design requires implementation and host validation; it is not a measured
fix yet.

### Other approaches

| Approach | Effect | Tradeoff/status |
|---|---|---|
| Refresh CLIs weekly with the runtime | Fewer changed images; small implementation | Loses daily CLI freshness; local edits still cause copies |
| Move immutable models to read-only clone-local mounts | ~1.41 GiB less runtime payload/remapping | Model files still occupy host disk; provision them before launch |
| Optional browser/model profiles | Real image and installation size reduction | Changes the capabilities available offline |
| Dedicated outer FUSE store plus inner writable storage off the outer rootfs | Candidate way to avoid remapping on any image update | Experimental; needs shared-store, nesting, performance, and cleanup tests on a real host |
| Run the outer workload as container root | Aligns the normal rootless mapping | Changes inner Podman behavior and isolation assumptions; previous nesting failure recorded |
| Squash layers, increase compression, reorder COPY, or skip warming | Does not resolve ownership mismatch | Compression helps transfer size; skipping warming moves the wait to first launch |

### Savings ranked by practicality

| Change | Measured payload affected | Consequence |
|---|---:|---|
| Keep both models outside the runtime image | 1,440.7 MiB | Preserve offline availability through pre-provisioned mounts; no equivalent reduction in total asset storage |
| Make Cypress optional | ~724 MiB including npm package | Cypress unavailable in that profile; its Electron is not replaced by Chrome |
| Make Firefox and WebKit optional | 593.5 MiB | Loses those engines' coverage; browser dependencies may offer additional unmeasured savings |
| Keep only system Chrome for both automation libraries | 389.0 MiB | Playwright callers must select `channel: 'chrome'`; different browser version/testing contract |
| Move CLIs out of runtime | ~525 MiB | See separate-update design; tools remain on host disk |
| Use a smaller rembg model | Much of the 976.9 MiB model | Quality/default behavior changes; make the selected model explicit everywhere |
| Omit Python bytecode during installation | Up to the observed ~125 MiB, before regeneration | Slower first imports; imports can recreate bytecode; measure startup impact |
| Replace full rembg web extra with a deliberately supported CLI dependency set | gradio + pandas alone ~121 MiB | Removes web UI/server capability; requires a coherent dependency definition and CLI test |

Do not add all these numbers together: some options are alternatives and some
overlap. No smaller model was downloaded or benchmarked for output quality.
The comment calling the current rembg model the best of all available models
is an unvalidated quality assertion, not audit evidence.

With all capabilities required, prioritize asset separation and update cadence
over deleting dependencies. `--no-install-recommends`, excluded host state,
cache mounts for apt/npm/pip, same-layer tarball cleanup, CPU-only Whisper,
headless OpenCV, and Puppeteer's shared Chrome are already useful savings.
Blindly deleting `~/.cache` would remove the offline browsers and Whisper model.

Deleting content in a later RUN does not remove the bytes from earlier image
layers. Any package/bytecode pruning must occur in the layer that introduces
the files, or in a builder stage before exporting the retained files. Keep
compilers, headers, and `php-dev` unless the coding environment is explicitly
allowed to lose native-extension development capability.

## Build and cache findings

**Argument scope causes unnecessary rebuilds.** All version arguments, model,
and timezone are declared before the first package RUN. RUN instructions
implicitly use in-scope build arguments; changing even a late tool's version
can invalidate the early package layer. `WHISPER_MODEL` is additionally used in
the early ENV. Declare arguments immediately before their required use and move
the model ENV down accordingly. A three-build Alpine fixture here produced
three cache hits unchanged, but only one after changing an argument used
explicitly only by the last RUN: the earlier RUN rebuilt too. This matches the
[Dockerfile cache rules](https://docs.docker.com/reference/dockerfile/#impact-on-build-caching).

**Weekly invalidation is broader than the apt refresh.** Advancing
`UBUNTU_REFRESH` rebuilds every following tool, browser and model layer because
they form one chain. Download caches help apt/npm/pip, but the browser/model
directories are deliberately committed payload and are fetched by invalidated
install layers. Independent browser/model/tool stages would decouple their
downloads from an apt refresh. The final assembly would still change and need
host remapping.

**Claude and Codex are not independent installs.** A changed Claude layer
invalidates the following Codex layer even when Codex's version is unchanged.
Each refresh stage also binds the complete npm metadata document; changes to
that document can affect its cache key, not just changes to `.version`. Resolve
validated version numbers outside the large image build, and use independent
installation targets.

**Build arguments are ignored by the wrapper.** A mocked invocation of
`bin/build --build-arg WHISPER_MODEL=base` called Podman with only
`--build-arg UBUNTU_REFRESH=2026-W36 . -t ai-box`. No user arguments are read.
The advertised model/timezone knobs therefore require calling Podman directly
today. A wrapper should either support them or reject them clearly. If it
accepts `--target`/`--tag`, its warming/tag assumptions must also be handled.

**Build state needs coordination.** `data/refresh` is written after image build
but before warming, so it records build success, not warm completion. No build
lock prevents two invocations from changing the tag, stamp, and shared caches
concurrently. Use a clone-local build lock and warm the exact image ID produced.
Keep explicit cache settings rather than depending on `BUILDAH_LAYERS` from the
environment. Normal failed builds can use `--force-rm`; force termination still
needs separate stale-build recovery. Do not automatically prune unrelated host
images or containers.

**Refresh is not a lockfile.** The version manifest records selected top-level
versions, not all pip/npm dependencies, apt package versions, model revisions,
base-image digest, and artifact hashes. Weekly freshness is a policy, not
reproducibility. Keep a resolved inventory/SBOM for a finished image and update
it separately from the decision to refresh.

## Runtime and script correctness

**Playwright regression, reproduced.** With Playwright 1.62.1 installed here:

```javascript
const { chromium } = require('playwright');
await chromium.launch();
// Fails: chromium_headless_shell-1234/.../chrome-headless-shell is absent.

const browser = await chromium.launch({ channel: 'chromium' });
// Succeeds: Chromium 151.0.7922.34.
await browser.close();
```

The Dockerfile and README incorrectly say removing the shell automatically
makes default launches use the full browser. Playwright documents the explicit
channel required for this mode in its
[browser installation guide](https://playwright.dev/docs/browsers#chromium-new-headless-mode).
Keep the size reduction only with an explicit caller contract. A version/list
check does not validate browser launching.

**Image removal changes intent on failure, reproduced.** The final expression
in `bin/images` is `test ... && podman ... rmi ... || podman ... pull ...`.
With a mock `rmi` returning 23, the script issued `pull` and returned success.
Use an explicit branch and propagate removal failure. `--remove` without image
arguments currently lists images instead of reporting missing operands.

**Shared-store concurrency.** `bin/images` deletes `db.sql` and `libpod` on EXIT,
including read-only listing invocations. Another `bin/images` or the direct
Podman command in the README may still be using that database. The underlying
storage library has its own locks, but the shell's deletion is outside that
lifecycle. Establish one serialized host entry point; the README's direct
`podman --root ... pull alpine:latest python:3.12-slim` example also incorrectly
assumes multiple image operands and bypasses the wrapper's cleanup/qualification.

**Diagnostics can hang.** `bin/missings` repeatedly calls `podman info`, image
inspection, `run`, and `ps` without a timeout. It can wait on the operation the
user is trying to diagnose. Read info once with a bounded timeout; report
busy/unavailable distinctly. `Native Overlay Diff` is a diff-optimization flag,
not a complete test of the mount program or shifting capability. Inspect those
fields directly. Normal diagnostics and long-running deep tests need different
time budgets.

**Compose DNS failed in this environment.** Two Alpine services started using
podman-compose 1.0.6, but the client could not resolve `web` for an HTTP request
to `http://web:8000`. A second isolated project failed all five retries. Its
network reported DNS enabled and the client had the network gateway as its
nameserver. Both projects were torn down. The cause is unresolved: this tests
the available nested environment, not a fresh host launch through `bin/run`.
It does not establish that the README's previously tested host configuration
has regressed, but means its compose-DNS claim was not reproduced here.

**Fixed-file benchmark can destroy data.** `diskperf` runs `dd ... of=tmpfile`
and then `rm tmpfile` in the writable workspace, twice. It also follows a
pre-existing symlink. This finding follows directly from the commands; the
destructive benchmark was not run. Use `mktemp` on the tested filesystem and
ensure cleanup runs after timeout or interruption.

**Paths and input validation.** The common script prologue leaves `$0` and
derived paths unquoted. A copied `bin/images` in a path containing spaces failed
before doing useful work. `.shellcheckrc` suppresses the warning that would
catch this. Volume `-v` syntax also cannot safely represent arbitrary colon
characters in host paths. `services` interpolates its database argument into
SQL without validating/escaping an identifier; validate the supported project
name before starting services. Its Redis startup has no readiness check.

**Host configuration edges.** Subuid/subgid checks inspect only the first
matching line, so usable multiple ranges are not correctly accounted for.
`bin/configure --dry-run` inside this container reported the first 999-ID range
and exited 1; this is not a host acceptance result. The suggested `sed` rewrite
to a hard-coded range is inappropriate advice where ranges already overlap or
are in use. Module persistence is only written when a device is currently
missing, and bare-root handling still depends on an existing `sudo` command.

## Isolation and supply-chain findings

- `bin/run` and `bin/build` lack the non-root guard already present in
  `bin/images`. The current script flags have to be evaluated as a rootless
  configuration; running them with sudo is outside that intended boundary.
- Masking covers top-level `.env`/`.env.*`, with suffix exemptions, and explicit
  `AI_BOX_MASK` files. Nested `.env`, credential files, readable Git config, and
  template files are not universally sanitized. If a workspace is also exposed
  through `~/repos` or another mount alias, a file masked at `/app` can remain
  readable through that alias. Read-only does not mean secret-free.
- `/var/lib/shared` is an OS-level read-write mount. The inner storage library's
  additional-image-store policy does not prevent an arbitrary process from
  modifying host-user-owned store files directly. The README's “only transient
  mountpoints are written” describes expected engine behavior, not enforced
  isolation. Consider a read-only lower store with transient mount/state outside
  it as a separately validated design.
- Cgroup limits are conditional; missing delegation silently omits them.
  `--memory` does not explicitly set the swap policy. Report the effective
  limits and define whether memory means RAM alone or RAM plus swap.
- `seccomp=unconfined` and `unmask=ALL` remain broad, documented compatibility
  choices. Do not replace them based solely on a one-container smoke test;
  validate nested run/build/compose before narrowing. `label=disable` concerns
  SELinux labeling; it must not be presented as proof that an AppArmor policy
  allows nested user namespaces. The previous audit's AppArmor explanation was
  not revalidated here.
- Outbound network and the writable workspace remain part of the trust boundary.
  The claim that nothing can reach the host is broader than a rootless container
  guarantees, especially for reachable network services and mounted files.
- The entrypoint invokes `install` and `setpriv` through a PATH beginning with
  user-owned directories. Use their absolute system paths before dropping UID.
- Base images, external package releases, and several transitive dependencies
  float. Publisher checksums are useful corruption checks; checksums obtained
  from the same publisher are not independent provenance. The manually fetched
  Chrome Packages file is not verified against a signed Release in this code.
  npm/pip integrity and TLS should not be described as independent signatures.
- CI action references float at tags and the workflow does not declare minimum
  `contents: read` permissions. Tightening those is straightforward maintenance.

## Implementation and acceptance order

1. Fix the confirmed correctness problems: Playwright contract/documentation,
   fixed benchmark filename, removal branching, build options, and root guards.
   Add small regression checks for the failed behaviors above.
2. Separate CLI updates from the runtime and validate atomic update/failure
   behavior. Measure before/after image ID, runtime launch time, and store growth
   on the real native-overlay host. A CLI-only update must preserve the runtime
   image ID and must not allocate another whole-image mapped copy.
3. Move model assets to separately versioned, pre-provisioned read-only mounts
   if a multi-artifact installation is acceptable. Test rembg and transcription
   with network disabled; ensure cache locks/temp files do not require writes
   to the read-only asset directory.
4. Fix ARG scope and separate large dependency stages. Compare an unchanged
   build, CLI-only change, helper-only change, model-only change, and weekly
   refresh. Record layer IDs/cache hits separately from runtime remapping time.
5. Introduce optional browser/model profiles only after choosing the required
   offline capabilities. Compare actual `podman image inspect` and `history`
   sizes, visible filesystem sizes, shared/unique host storage, and compressed
   transfer sizes as distinct measurements.
6. Extend host acceptance coverage to nested run, build FROM shared storage,
   compose service-name DNS and published ports, browser launch, workspace file
   ownership, cold/warm launch time, and termination cleanup. Use isolated test
   names/stores and measure only those; do not prune unrelated user state.

The existing rootless design, clone-local state, late local COPY instructions,
package cache mounts, CPU-only inference, and explicit nesting configuration are
worth retaining. The large gains come from reducing the bytes coupled to each
update, followed by choosing which optional capabilities belong in the image.
