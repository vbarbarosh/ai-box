# ai-box audit — 2026-09-02

Full audit of the repository at commit `4c2cdc7` (branch `main`, clean tree).
Covers security and isolation, script correctness, the Dockerfile and its
supply chain, documentation accuracy, and CI.

## Scope and method

Everything in the tree was read: `Dockerfile`, the four host scripts under
`bin/`, the entrypoint, every helper under `files/`, the container configs,
the CI workflow, the lint configs, `README.md` and `notes/goal.md`.

What was actually exercised:

- `bash -n`, shellcheck 0.11.0 at the CI level (`-S warning`) and at `-S style`,
  hadolint 2.15.1 with and without the project's ignore list, `node --check`
  and a Python AST parse. All clean with those versions. *Correction, same
  day:* the GitHub run for this commit failed at hadolint, because
  `hadolint-action@v3.1.0` bundles hadolint 2.12.0, which raises DL3042 on the
  two `pip install` lines (`Dockerfile:202`, `:237`). Reproduced locally with
  2.12.0; 2.13 and later recognise the pip cache mount and stay quiet. See L14.
- The workspace guard, the `.env` masking loop and the subuid block allocation
  were copied out of `bin/run` and `bin/configure` and run against synthetic
  directories and subuid files.
- Upstream checks: every pinned version resolves (Node 24.20.0, Playwright
  1.62.1, Puppeteer 25.9.0, Cypress 14.5.4, ImageMagick 7.1.2-30, oxipng
  10.2.0); the GitHub release API does expose the `digest` field the Dockerfile
  relies on; Ubuntu noble ships podman 4.9.3 and podman-compose 1.0.6 as the
  README says; the current `@anthropic-ai/claude-code` npm package was
  downloaded and inspected; `parallel` depends on `procps`, so `free` in
  `hwdata` exists in the image.

What was **not** exercised: this host has no podman and no reachable Docker
daemon, so the image was not built and the box was not started. Every runtime
claim (nested `docker run`, startup time, the id-mapped layer copy, cleanup on
SIGKILL) is taken from the README, not re-measured. `bin/build && bin/missings
--deep` on a real host remains the acceptance test, as the CI file says.

## Verdict

The project does what `notes/goal.md` asks for, and the way it gets there is
sound: rootless Podman outside, Podman inside, no `--privileged`, no socket,
and every non-obvious flag or layer carries a comment that says why it is
there. Lint is clean, the guard logic behaves exactly as documented, and the
download-verification ordering (checksum first, artifact second) is done
consistently.

The findings below are mostly about the edges of the isolation story: the
secret-masking promise is broader in the README than in the code, the
rootless assumption is not enforced, and the nesting silently depends on a
host AppArmor policy that nothing checks. None is a bug in the happy path.

Severity key: **M** = worth fixing before relying on the claim, **L** = small
correctness or robustness gap, **D** = documentation, **I** = information.

## Security and isolation

### M1. Secret masking covers only top-level `.env*`

`bin/run:67-73` masks `$PWD/.env` and `$PWD/.env.*` (minus the template
suffixes) by binding `/dev/null` over them. Verified: `backend/.env` in a
monorepo is **not** masked unless named in `AI_BOX_MASK`, and neither are
`.envrc` (direnv, routinely holds exports), `.npmrc` / `.pypirc` / `.netrc`
with tokens, `*.pem`, `credentials.json`, or `config/*.local.*`. The README
line "secrets never enter the box" and `.gitignore`'s comment promise more than
the glob delivers.

Also readable: `.git/config` (mounted read-only, but readable). Remotes of the
form `https://user:token@host/…` and any credential-helper config in it are
visible to the agent.

Suggestions, in order of value:

1. Walk the workspace for `.env` and `.env.*` at any depth (`find -name`,
   pruning `node_modules`, `.git`, `vendor`), not just the top level.
2. Add `.envrc`, `.npmrc`, `.netrc`, `.pypirc` to the default mask set.
3. Reword the README to "top-level `.env` files are masked; use
   `AI_BOX_MASK` for anything else", or do (1) and keep the sentence.
4. Optionally mask `.git/config` with a sanitized copy when it contains `@`
   in a URL. Cheap to detect with `git config --get-regexp 'remote\..*\.url'`.

### M2. Nothing stops `bin/run` from running as real root

The whole isolation argument (`bin/run:170-171`, README "this is not host
root") rests on the outer podman being rootless. `bin/run` never checks
`id -u`. Run as root, the same command line is rootful podman with
`seccomp=unconfined`, `unmask=ALL`, `label=disable`, `/dev/fuse` and
`/dev/net/tun`, with the workspace and `~/repos` mounted from root's view. And
`bin/configure --as-root` (`bin/configure:33-43`) explicitly supports "root
really is the user who will run it", which makes that path look sanctioned.

Suggest: refuse `id -u = 0` in `bin/run` with a one-line reason, and either
drop `--as-root` from `bin/configure` or have it print the same warning.

*Update, same day:* `--as-root` is gone from `bin/configure`; bare root now
always stops with a message that says the box is rootless. The `bin/run`
half is still open.

### M3. Nesting depends on host AppArmor policy that nothing checks

Ubuntu 24.04 and later set `kernel.apparmor_restrict_unprivileged_userns=1`
(confirmed on the kernel under this host). An unconfined, unprivileged process
then cannot create a user namespace unless an AppArmor profile with `userns`
attaches to its executable. Rootless podman on the host works because Ubuntu
ships such a profile for `/usr/bin/podman`. The **inner** podman works for the
same reason: `--security-opt label=disable` leaves the box unconfined, and the
host profile attaches by path to `/usr/bin/podman` inside the box on exec.

Consequences:

- `label=disable` is load-bearing, and it is the one flag in `bin/run:147-171`
  without a comment. Worth a line, since every other flag has one.
- On a host where that profile is absent or AppArmor is configured differently
  (Debian, a hardened Ubuntu, a future profile rename), the inner engine fails
  with an opaque `EPERM` and `bin/missings` reports the host as ready.
- `bin/missings:112-117` checks `user.max_user_namespaces` but not the
  AppArmor sysctl or the profile.

Suggest: in `bin/missings`, when the sysctl is `1`, require
`/etc/apparmor.d/podman` (or `aa-status` listing it) and report it as
required-for-nesting. Not verified here beyond the sysctl value, because the
box could not be started on this host.

### M4. `seccomp=unconfined` where a narrow profile would do

The README already says a custom profile "adding just `sethostname` would
recover most of it". The profile is not in the tree. Podman's default profile
allows `sethostname` only with `CAP_SYS_ADMIN`, which the box does not have,
so the fix is a copy of `/usr/share/containers/seccomp.json` with
`sethostname` (and `setdomainname`) added unconditionally, shipped as
`files/seccomp.json` and passed as `--security-opt seccomp=$scriptdir/../files/seccomp.json`.
The inner runtime may need one or two more calls; `bin/missings --deep` will
say which. `unmask=ALL` has to stay for the reason in the comment.

### L1. The entrypoint runs as root with user-writable directories first on `PATH`

`Dockerfile:39` puts `/home/ubuntu/bin` and `/home/ubuntu/.local/bin` at the
front of `PATH` for every user, including the root that runs
`files/docker-entrypoint:15-26` at container start. Neither directory persists
across runs (only `~/.claude`, `~/.codex` and the two JSON files are mounted),
so nothing written in one session runs as root in the next. Still, `install`
and `setpriv` should be spelled `/usr/bin/install` and `/usr/bin/setpriv`
so the property does not depend on what is mounted later.

### L2. `--memory` alone caps RAM, not RAM plus swap

Podman follows Docker here: with `--memory` set and `--memory-swap` unset, the
swap limit defaults to twice the memory limit. On a host with swap the box can
take three quarters of RAM plus the same again in swap before the OOM killer
acts. Add `--memory-swap "$memory"` next to `--memory` in `bin/run:121-123`
to make the cap mean what the README says. `AI_BOX_PIDS=4096` counts threads,
not processes; Chrome, MySQL and a compose stack with a parallel test runner
can reach it. Fine as a default, worth a sentence in the README.

### I1. Threat model, stated plainly

The box protects the host from the agent. It does not protect the workspace,
or anything the agent can read, from the agent:

- The workspace is read-write. `Makefile`, `package.json` scripts,
  `.vscode/tasks.json`, `.envrc`, `.claude/settings.json` hooks and the like
  run on the host the next time *you* invoke them. `.git` being read-only is
  the right call: hooks cannot be planted.
- Outbound network is unrestricted, so anything readable (workspace,
  `~/repos`, the agent's own OAuth tokens in `~/.claude.json`) is exfiltrable
  by a prompt-injected agent. On a cloud VM the instance metadata endpoint is
  reachable from the box too.
- `~/repos` read-only exposes every repository, including their `.git/config`.

None of this is a defect. It belongs in the README's "worth knowing about"
paragraph so users calibrate what they run from the box.

## Script correctness

### L3. Paths with a colon break the bind mounts

`-v "$workspace:/app"` (`bin/run:177`) and the `/dev/null:/app/$f:ro` masks
use the colon-delimited form. A workspace or masked file whose path contains
`:` mounts the wrong thing. `--mount type=bind,src=…,dst=…` has no such
ambiguity. Rare, but the guard at the top of the script shows the author cares
about this class of surprise.

### L4. `AI_BOX_MASK` silently drops absolute paths

`bin/run:68-71` strips `$workspace/` and then tests `$workspace/$f`. An
absolute path outside the workspace, or a typo, is skipped with no message.
A `echo "warning: AI_BOX_MASK: $f not found" >&2` on the `continue` would make
a mis-typed mask visible instead of quietly unmasked.

### L5. `.git` as a file (worktrees, submodule checkouts) is mounted over itself

`test -e "$workspace/.git"` is true for a worktree's `gitdir: /elsewhere` file.
It is then bound read-only over itself and the real git directory is not in
the box, so `git` inside reports a broken repository. Either skip the mount
when `.git` is a file, or mount the resolved `gitdir` as well. Edge case.

### L6. `services` small things

- `redis-server --daemonize yes` (`files/bin/services:88-92`) writes its
  pidfile to `/var/run/redis.pid` by default; as `ubuntu` that fails with a
  warning in the log. Add `--pidfile $rundir/redis.pid`.
- All three services bind `127.0.0.1`, so containers started by the inner
  engine cannot reach them (they are on a netavark bridge, and
  `host.containers.internal` points at the box's other addresses). Either
  document it or offer `services --bridge` that binds `0.0.0.0`; inside the
  box that is still not host-reachable.
- `$name` is interpolated into SQL between backticks and into an `mc` path
  unquoted. Dev tool, own user, low stakes. A `case "$name" in *[!A-Za-z0-9_-]*)`
  reject would close it.

### L7. `bin/build` cosmetics

`bin/build:162` lists `130` and `$((128+2))` in the same case arm; they are
the same number. Harmless.

### L8. `hwdata` and `netdata` carry the only style-level shellcheck notes

`$[ ]` arithmetic, `let`, `egrep`, `read` without `-r`. All in
`files/bin/hwdata` and `files/bin.host/netdata`, both inherited scripts. CI
runs at `-S warning` so they pass; a `-S style` pass would be a small clean-up.

## Dockerfile and supply chain

### L9. Unauthenticated GitHub API calls have a 60/hour ceiling

`Dockerfile:303` and `:318` query `api.github.com` for asset digests. The
unauthenticated limit is 60 requests per hour per source IP (58 remaining
from this host at audit time). Behind a shared NAT or in CI the call returns
403, `jq` yields nothing, and the build stops at `test -n` with no message
that says why. Suggest: print the API response on failure, and accept an
optional `--secret id=github_token` so a busy network can authenticate.

### L10. No `LANG` in the image

Nothing sets a locale (`grep LANG Dockerfile` is empty). Python 3 coerces to
UTF-8 on its own, Node does not care, but PHP, `sort`, `grep`, `man` and
several CLIs fall back to `POSIX`. `ENV LANG=C.UTF-8` is available without
the `locales` package and removes a class of "invalid multibyte" surprises.

### I2. The two agent CLIs are installed the way the comment says

The current `@anthropic-ai/claude-code` package (2.1.258) is a wrapper whose
postinstall copies a native binary from an npm *optional platform package*
(`@anthropic-ai/claude-code-linux-x64`), not from an external URL. npm verifies
both tarballs, so the comment at `Dockerfile:439-442` still holds. Codex is
structured the same way (`@openai/codex-linux-x64`). Both need install
scripts enabled, which they are.

### I3. What "every download is checksum-verified" actually covers

Node, Composer, MinIO, `mc`, yt-dlp, oxipng, ImageMagick and Chrome are
verified against a publisher checksum fetched *before* the artifact, with the
straddle case handled. Not covered by that sentence: `pecl install redis`
(TLS only), and the browser downloads done by `playwright install`,
`puppeteer browsers install` and Cypress (each tool's own mechanism). The
README sentence is close enough; a parenthetical "except PECL and the browser
fetches, which rely on their own tooling" would make it exact.

### I4. Image size

Four Chromium-family browsers land in the image (Playwright's Chromium,
Puppeteer's Chrome, Cypress's bundled Electron, Google Chrome) plus Firefox and
WebKit, plus a whisper model and the u2net model. All intentional. If size ever
matters, `puppeteer` can be pointed at Playwright's Chromium with
`PUPPETEER_EXECUTABLE_PATH` and its own download skipped.

### I5. Things checked and found correct

- 14 `--mount=type=cache` lines, matching the README's count.
- Six pinned build args, matching "only six versions are pinned".
- `/etc/subuid` inside gives 65,534 ids in two blocks around uid 1000; an
  inner image with a uid above 65,535 will fail, which the README implies.
- COPY layers are last; `.dockerignore` limits context to `Dockerfile`,
  `.dockerignore` and `files/` minus `bin.host/`.
- `ADD` of the npm metadata in the two refresh stages is what makes the final
  two layers follow a release; the `chmod 0444` is needed because `ADD` from a
  URL lands as 0600 and the layer that reads it runs as `ubuntu`.
- `newuidmap`/`newgidmap` switched from setuid to file capabilities, as the
  comment explains; `podman-docker` provides `docker`; `nodocker` marker set.

## Documentation

### D1. README helper table is missing two scripts

`files/bin/` also installs `diskperf` and `showhomedir`; neither is in the
"Helpers on the PATH" table. Both are also absent from the README's list of
things that "only make sense on a real host", so they read as unintended.

### D2. Overclaims to soften

- "secrets never enter the box" (see M1).
- "Every download is checksum-verified" (see I3).
- "nothing it runs can reach the host" (`bin/run:171`): true for the host's
  filesystem and processes; not true for host services listening on a LAN
  address, or the cloud metadata endpoint (see I1).

### D3. Two aliases, one agent

`Dockerfile:194` aliases `codex` to `-a never -s danger-full-access`. Claude
has no equivalent (`--dangerously-skip-permissions`). Inside a throwaway box
either choice is defensible, but the asymmetry is unexplained. One comment
line would do.

## CI

The workflow (`.github/workflows/lint.yml`) is the right shape: syntax, lint,
executable bits, and an honest note that the real test needs a real host.

- L11. Add `permissions: contents: read` at the top; the default token has
  write scopes it never uses.
- L12. `hadolint/hadolint-action@v3.1.0` and `actions/checkout@v4` are
  tag-pinned. SHA pins are the usual hardening for a repo whose theme is not
  trusting upstreams by default.
- L14. **CI is red on `main`.** `hadolint-action@v3.1.0` runs hadolint 2.12.0,
  which flags DL3042 (pip without `--no-cache-dir`) at `Dockerfile:202` and
  `:237`. `--no-cache-dir` would defeat the BuildKit cache mount those layers
  exist to use, so the right fix is one more line in `.hadolint.yaml`:
  `- DL3042  # pip's cache is a BuildKit cache mount, not in the image; the action's hadolint 2.12 predates that check`.
  Hadolint 2.13+ already understands the mount, so the ignore can go when the
  action moves on.
- L13. `bin/configure --dry-run` needs no sudo and runs on `ubuntu-latest`;
  adding it as a step would catch a regression in its argument handling or
  subuid arithmetic. `bin/missings` cannot run there (no podman) but
  `bin/missings || true` would still print its report into the log.

## Strengths worth keeping

- Rootless outside and inside, no daemon, no socket, no added capabilities.
- `.git` mounted read-only: no hook planting, history untouched.
- Agent state under XDG data, not the user's own dotfiles.
- Checksum-before-artifact ordering, a version manifest in the image, and a
  weekly refresh token instead of `apt` pins.
- The `$HOME` guard, tested here against `/`, `$HOME`, a parent of `$HOME`,
  a symlink to `$HOME` and a symlink into a project: all handled correctly.
- Idempotent `bin/configure` that picks a non-colliding subuid block (tested
  with two existing users, an empty file, and a gap).
- Every non-obvious line in `Dockerfile` and `bin/run` says why it is there.

## Suggested order of work

1. M1 (nested `.env`, `.envrc`, README wording) and M2 (refuse root). Both are
   small diffs to `bin/run`.
2. M3: an AppArmor check in `bin/missings` plus a comment on `label=disable`.
3. M4: ship the seccomp profile, validate with `bin/missings --deep`.
4. L2, L1, L10: one line each.
5. D1, D2, D3 in the README.
6. CI hardening (L11-L13).
