# The id-mapped layer copy — what it is and what does not fix it

2026-09-04. Written after a day spent trying to remove the copy that
`bin/build` warms at the end of every build, and failing. Everything below was
measured on this host (podman 5.7.0, crun 1.21, kernel 7.0.0-30, rootless,
uid 1000, one subordinate range of 65536) or read out of the sources named.
Recorded so nobody — including a later reader of `bin/build`'s comments —
spends the same day twice.

## The cost

`bin/build`'s last step takes ~125s and writes ~8.5 GB, once per image id.
Since the two agent CLIs are installed from an every-build layer, that is once
a day. At one build a day it is ~3.1 TB/year of writes; this machine's SSD
reports 33.7 TB written for 7% of its rated life, so the copy alone is about
0.65% of the drive per year, spent on nothing but renumbering owners.

## Why it happens

`bin/run` starts the box with `--userns=keep-id:uid=1000,gid=1000`. That is
not the mapping the image store is written with, and containers/storage has to
reconcile the two.

The default rootless mapping — the one every image in the store is written
under — is:

| inside the container | on disk |
|---|---|
| 0 (root) | 1000, your own uid |
| 1 … 65536 | 100000 … 165535, your subordinate range |

There is no row where 1000 means 1000. Your own uid is spent on *container
root*, which is what makes files that root creates inside a container land as
yours. Verified directly against a stored image: in `overlay/<layer>/diff`,
`/bin` and `/boot` (root-owned inside) are stored as uid 1000, and
`/home/ubuntu` (uid 1000 inside) is stored as the first subordinate id.

`keep-id:uid=1000` asks for your uid to sit at container 1000 instead, which
shifts every other row too. podman builds that map in
`pkg/util/utils.go:getRootlessKeepIDMapping`; for uid 1000 and a 65536-wide
range it is exactly:

    {ContainerID: 0,    HostID: 1,    Size: 1000}
    {ContainerID: 1000, HostID: 0,    Size: 1}
    {ContainerID: 1001, HostID: 1001, Size: 64536}

(ids in the rootless coordinate space: 0 is your own uid, 1..N the range.)

Reconciling that with the layers on disk happens in
`containers/storage/store.go:imageTopLayerForMapping`. It looks for a layer
that already matches — `reflect.DeepEqual` over the whole map list — and if
there is none it makes one: `CreateFromTemplate` with the image's top layer as
the template, then `drivers/overlay.UpdateLayerIDMap`, whose own comment reads
"Mount the new layer and handle ownership changes and possible copy_ups in
it". Chowning every path through an overlay mount copies up every file. So:

- the cost is the **whole image**, not the layers that changed;
- it is paid on **every new image id**, whichever layer changed;
- reordering the Dockerfile so the volatile layers come last does nothing.

`bin/build`'s progress line ("only the layers that changed") is wrong on this
point and should be corrected.

## Why the fast path is unreachable rootless

`canUseShifting` (`store.go`) defers to the driver's `SupportsShifting`
(`drivers/overlay/overlay.go`):

- **native overlay**: `supportsIDmappedMounts()` →
  `checkAndRecordIDMappedSupport`, which opens with

      if os.Geteuid() != 0 { return false, nil }

  It never asks the kernel. Rootless never gets idmapped lower dirs, on any
  kernel. This is not a version problem and will not age out.
- **fuse-overlayfs** (`mount_program` set): supported, provided both maps are
  contiguous. keep-id's map above *is* contiguous by `idtools.IsContiguous`
  (sort by host: 0,1,1001 end to end; sort by container: 0,1000,1001 the
  same), so this really would skip the copy — but it is already recorded here
  that fuse-overlayfs breaks nested `docker build` against the shared image
  store, so it stays rejected.

Custom idmapped **bind mounts** are out for the same reason. Tested:

    podman run -v src:/x:idmap=uids=1000-1001-1 …
    Error: crun: mount_setattr `/x`: Operation not permitted

The kernel will not let an unprivileged user idmap a filesystem mounted in the
initial user namespace. Plain `:idmap` with no arguments is accepted but is a
no-op — it asks for the mapping the container already has.

## What was tried and does not work: building under the mapping

The idea: build the image with `--userns-uid-map` / `--userns-gid-map` set to
the triples above, so the layers carry keep-id's mapping, `DeepEqual` matches
at run time and nothing is ever copied. It fails, in two different ways, and
both were paid for in full.

**With the build cache.** buildah creates a working container at every step,
including cached ones. A cache hit hands it a layer written under the old
mapping, and making a container from that layer is the copy — so the whole
image is copied *per cached step*. Measured: ~110-116s per `Using cache` line,
one `<layer>-working-container` per step in `podman ps -a --external`, their
timestamps two to three minutes apart in step order. An hour got as far as
step 31 of 62. Killed; `podman image prune -f` returned 75 GB.

**With `--no-cache`.** Rebuilding every step for real does not help either,
because buildah commits each step's layer in the *store's* mapping regardless
of `--userns-*-map` — that flag governs the namespace `RUN` executes in, not
how the result is stored. So every step still needs an ID-mapped copy of the
one below it, and the copies grow with the image. It ran 63 minutes and died
at step ~37 with

    creating build container: creating an ID-mapped copy of layer "8c818f20…":
    error during chown: storage-chown-by-maps: lchown
    home/ubuntu/.cache/ms-playwright/…/chrome: no space left on device

having taken the disk from 139 GB free to 9 GB — ~130 GB of copies.

**Verdict: there is no way to make a built image carry a run-time id mapping
via `podman build`.** Do not try this again.

## Collateral worth knowing

- **`--mount=type=cache` directories carry the mapping too.** They live on the
  host at `${TMPDIR:-/var/tmp}/buildah-cache-$UID/<target>`, chowned to
  whichever host id the mount's `uid=1000` meant when they were created. Build
  under a different mapping and npm meets a cache it cannot write: the build
  dies at the first `npm install` with EACCES. They are only repairable from
  inside a user namespace (`podman unshare chown -R …`, or delete and let them
  refill).
- **buildah leaks working containers when a build is terminated.** 65 of them
  from a build two days earlier were still pinning images and disk.
  `podman system prune --build -f` is the one that removes them, and it has to
  run *before* `podman image prune -f` or the images stay pinned.
  `podman system prune --external -f` sweeps what is left unreferenced.
- **`podman info` takes the store lock.** While a copy or a build holds it,
  every podman command — `bin/missings` included — blocks. One `bin/missings`
  run waited 5m45s at "host storage" with 1.7s of CPU. Worth a `timeout`
  around the podman calls in that script; it is the tool you reach for when
  something is already wrong.

## What is actually left

Only three, and each costs something elsewhere:

1. **fuse-overlayfs for the host store.** Removes the copy outright. Rejected
   here because it breaks nested `docker build` against the shared image
   store. Possibly revisitable if the inner store were moved off the box's
   rootfs onto a volume, which is why fuse-on-fuse breaks — untested.
2. **Run the box as uid 0.** No mapping is needed at all if the process inside
   is the id the store already gives your uid: container root. Costs the inner
   engine — podman decides rootless from euid, and rootful crun builds `/dev`
   with `mknod`, which a user namespace refuses. Measured:
   `podman run --rm --user 0 alpine mknod /tmp/n c 1 3` → "Operation not
   permitted". The non-root user inside is load-bearing for nesting.
   (`rootless.IsRootless()` also returns true when euid is 0 but CAP_SYS_ADMIN
   is absent — an untested door.)
3. **Stop changing the image daily.** The copy is per image id, so the cheapest
   fix is to not mint one every day: keep the two agent CLIs out of the image
   and update them inside the box. It trades away "you rebuild this repo, not
   install it", which is why it has not been done.

Until one of those is taken, the copy is the price of `--userns=keep-id` on
native overlay, and `bin/build` warming it once per build — while you are
already waiting — remains the right place to pay it.
